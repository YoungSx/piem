# 安全與隱私

[← 回到 README](../README.zh-TW.md) · [English](security.md) · [简体中文](security.zh-CN.md) · [日本語](security.ja.md)

Piem 把你的筆記交給一個模型服務商，並且讓一個代理去改它們。這兩件事都是重
點，也都值得直說，而不是讓你在某個設定頁裡自己發現。

## 什麼會離開你的儲存庫

發給你設定的模型服務商：

- 你的提示與對話歷史；
- **你正打開的那篇筆記**——路徑和完整正文——每一輪都發，無論你的問題是否與它
  有關；
- 工具回傳的儲存庫內容——筆記正文、搜尋結果、檔案清單、frontmatter；
- 代理回顧時讀取的記憶和過往對話摘錄；
- 工具結果，包括 `web_fetch` 抓回來的東西；
- 你暫存的圖片附件。

額外發給某台 MCP 伺服器的：由它公開的那個工具的呼叫參數。每個 MCP 工具的描述
裡都寫著這件事，所以模型也知道。

準備內建技能時，會向 GitHub 發送 GET 請求，下載與目前外掛版本相符的資源。
GitHub 及其下載主機會收到資源 URL（包含外掛版本）、裝置 IP 和普通請求中繼資料。
這次下載不攜帶筆記、對話或服務商密鑰。資源是經過摘要校驗的 Markdown，寫入
`Piem/builtin-skills/`；不執行指令碼，也不會獨立於外掛追隨更新的 Release。

內建的 `switch_model` 可以把目前對話切換到另一個已有密鑰的模型，並保存選擇。
新的服務商會在下一次請求收到對話和正常筆記脈絡。`/continue` 會發出正常計費
的模型請求。交接標註只在請求脈絡說明前面的模型名稱，不會發送到獨立服務。
這些擴充功能只執行隨外掛發布的程式碼，不能載入本機或遠端指令碼。

`web_search` 把查詢和指定網址發給目前模型服務商的原生搜尋介面，不額外附帶
整段對話。搜尋和來源抓取由該服務商處理，適用其條款與搜尋費用；Piem 不會
靜默換用另一家。`/clarify` 只把草稿和改寫指引交給目前或明確固定的模型，不
附帶目前筆記或聊天歷史。結果留在輸入框，等你選擇發送。`context_compact` 在
本機保留舊歷史、保存摘要分支，再發出普通模型請求繼續任務。

停止會取消擴充功能的後續操作並丟棄遲到結果。Obsidian 的 `requestUrl` 無法中止
已經發出的原生網路請求，因此請求可能繼續完成或產生費用。宿主會追蹤它直到
結束；它不能再覆寫草稿、改動另一聊天或重啟已停止的任務。

錯誤報告與效能資料預設發給 Piem 維護者，可以在 **設定 → Piem → 擴充能力**
關閉分享，詳情見下文。

實踐上的結論：**讓它對著一個你願意發給你的模型服務商的儲存庫。** 搜尋碰到哪個
檔案就會列出哪個檔案，而模型看得見那份清單。

## OpenTelemetry 發送

內建的原版 `b1tank/pi-otel` 擴充功能把追蹤、指標和生命週期日誌發給 Piem 維護者，
位址為 `https://otlppiem.shangxin.me`。
**設定 → Piem → 擴充能力 → 分享錯誤報告與效能資料** 預設開啟。
關閉後立即停止後續報告並丟棄未發送資料；已經發出
的請求無法撤回。重新開啟後需重載 Piem 才會恢復分享。目標服務除了遙測資料，
還會收到裝置 IP 和普通 HTTP 中繼資料，因此報告並非匿名。

發送內容包括會話 ID、模型和工具名稱、耗時、token 用量、報告的費用及成功或
失敗狀態。提示詞、回覆、系統指令、工具參數與結果、會話路徑、服務商請求正文
和回應標頭的採集保持關閉。**模型錯誤文字仍會進入追蹤狀態和例外事件**；錯誤若
帶有筆記內容，這些內容即使在正文採集關閉時也可能發出。請把 Collector 當作
會接收敏感診斷資訊的目標。

Piem 經宿主管理的背景 `requestUrl` 通道發送 OTLP/HTTP JSON，在固定位址後
分別加上 `/v1/traces`、`/v1/metrics`、`/v1/logs`。設定中不提供位址修改，舊的
自訂位址也不再使用。鑑權由閘道處理，外掛中不保存收集服務憑證。服務商密鑰
和電腦環境變數不會傳給擴充功能。分享偏好存入外掛資料，可能隨儲存庫同步。

指標每 60 秒發送，追蹤和日誌獨立批次發送。關閉會話或卸載 Piem 會停止自有
計時器，並給最後發送留下有限時間。Collector 不可用或網路慢時，最後一批可能
丟失。停止目前回答不會關閉這段對話的遙測。已經發出的原生請求可能在宿主停止
等待後繼續完成。本次接入不追蹤所有子代理內部呼叫。

## 沒有確認步驟

代理可以直接 `write`、`edit`、`move_note`、`trash_note`。沒有對話框，沒有等你
批的 diff，沒有「你確定嗎」。

一個例外，它由程式碼執行而不是擺一個對話框：設定目錄（`.obsidian/`）唯讀。代理
可以讀你的設定和已裝外掛的資料——見[代理的工具](tools.zh-TW.md#代理的工具)——
而任何對那裡的寫入嘗試都會得到一句明確的拒絕。

這是一個刻意的產品決定，不是缺失的功能。你可以這樣應對：

- 只在你願意被改動的儲存庫上用 Piem。
- 每輪之後讀一遍對話記錄——每處改動都來自一次工具呼叫，每次工具呼叫都在那兒。
- 把儲存庫放進版本控制，或者靠 Obsidian 的檔案恢復。`trash_note` 走的是
  Obsidian 的垃圾桶，所以刪除按常規辦法就能撤回。

## 你的密鑰存在哪

記憶筆記是隨儲存庫存儲和同步的普通 Markdown。`vault-memory` 技能要求代理避開
密鑰和密碼，但它不是密鑰偵測器。恢復依靠你儲存庫的檔案恢復或版本控制。刪除
目前事實不會刪除每日日誌、來源聊天或上述恢復系統中的副本。
見[記憶與過往對話](tools.zh-TW.md#記憶與過往對話)。

API 密鑰和 MCP Bearer 權杖隨 Obsidian 外掛資料存儲。

- **桌面端：** 寫進 `data.json` 之前先用 Electron `safeStorage` 密封——Windows
  上是 DPAPI，macOS 上是 Keychain，Linux 上是 libsecret。
- **行動端，以及沒有鑰匙串的桌面：** 明文存在 `data.json` 裡。那裡沒有可以拿
  來密封的東西，而假裝有比說出來更糟。

密封過的密鑰只能在密封它的那台裝置上解開。所以儲存庫同步**不會**把可用的密鑰帶
到另一台裝置上：每台裝置各輸一次。這更像是特性而不是限制，但它確實是「為什麼
我手機上的密鑰是空的」的答案。

優先用受限或低額度的密鑰。這一點外掛替你強制不了。

## Obsidian 審核會點名的能力

Piem 是一個代理外掛，所以做它該做的事，就需要一些 Obsidian 社群外掛審核會明確
點名的能力。這裡就用審核的同一套詞彙把它們列出來。沒有一項是缺陷或權宜之
計——每一項都在承載某個功能，而且沒有一項會把任何東西發到上面描述之外的地方。

**直接檔案系統存取。** 桌面端外掛透過 Electron 的 `require` 拿到 Node 的
`fs`，讀取使用者層級技能目錄（`~/.pi/agent/skills`、`~/.agents/skills` 和你設定的
額外目錄），因為儲存庫 API 看不到這些檔案。`read_skill` 可按需讀取所選技能的
UTF-8 文字資源，單檔最多 1 MiB，並校驗真實路徑仍位於該技能目錄內。
絕對路徑、隱藏路徑、向上跳轉和越界符號連結都會被拒絕。讀到的文字與其他工具
結果一樣發給目前模型，已讀取的資源會在壓縮後保留。這條存取唯讀，不提供 shell
執行；普通檔案工具仍限制在儲存庫內。行動端宿主不提供 `require` 時，使用者層級
技能顯示為不可用，不會導致外掛載入失敗。

**儲存庫列舉。** 搜尋和任務工具會呼叫 `vault.getFiles` /
`vault.getMarkdownFiles`，它們列出儲存庫裡每個檔案的完整路徑。只要一次搜尋或任
務查詢碰到它們，模型就看得見那份清單。這是「搜我的儲存庫」這件事本身的固有含
義。

**剪貼簿存取。** 只出不進：訊息回覆、日誌行，以及設定裡的複製密鑰操作會呼叫
`navigator.clipboard.writeText`。Piem 從不讀剪貼簿。貼上進來的圖片走的是編輯
器自己的 paste 事件，不是一次剪貼簿讀取。

**執行期 base64 編碼。** 圖片附件在作為模型內容發出去之前用 `btoa` 編碼。這就
是它的全部用途——程式碼裡沒有任何地方解碼混淆過的載荷。

**網路請求。** 大約二十處呼叫點，全部經由同一個傳輸層：模型服務商的串流、連線測
試、models.dev 目錄建議、遠端 MCP 伺服器、技能匯入、內建技能準備、`web_fetch`
工具，以及開啟診斷分享時的 Piem OpenTelemetry Collector。你在
`requestUrl` 與 `fetch` 之間的選擇只管住真正在乎串流的那部分——模型串流和連線測
試；目錄、技能匯入、內建技能準備、`web_fetch` 和遙測固定走 `requestUrl`，因為它們讀的是完整回應，
還必須夠得到那些不發 CORS 標頭的主機。出網行為集中在一處可查，而不是散落在程
式庫各處。

內建技能準備在 15 秒後停止等待，不會在失敗後迴圈重試。卸載會取消準備任務，
防止遲到回應發起寫檔案操作。Obsidian 的 `requestUrl` 無法物理取消已經發出的
請求，因此停止等待後，底層請求仍可能繼續完成。已有檔案可離線使用；擴充能力
中的 **重試準備** 和 **恢復缺失檔案** 是顯式的恢復入口。
