# 擴充 Piem

[← 回到 README](../README.zh-TW.md) · [English](extending.md) · [简体中文](extending.zh-CN.md) · [日本語](extending.ja.md)

給 Piem 加東西有兩條路：**技能**，是它能遵循的指令；**MCP 伺服器**，是它能呼
叫的工具。

## 技能

技能是一段可重複使用的指令，代理能遵循它，你也能在輸入框敲 `/` 直接呼叫。
Piem 按以下順序合併三處技能，後面的同名技能覆蓋前面的：

1. **內建** —— `Piem/builtin-skills/<名字>/SKILL.md` 中的標準檔案。包含
   `summarize`、`link-graph`、`tag-organize`、`find-skills`、
   `efficient-web-research`、`vault-memory`、`distill-skill`、
   `mineru-parse` 和 `build-knowledge-base`。
2. **使用者層級** —— 桌面端的 `~/.pi/agent/skills`、`~/.agents/skills`，以及設定
   中可選的額外目錄。這些目錄內部仍沿用現有優先序。
3. **筆記庫** —— `Piem/skills/<名字>/SKILL.md` 中自己寫的或匯入的技能。
   筆記庫裡的同名技能優先於另外兩處。

`vault-memory` 教代理回顧和自主維護有用事實；`distill-skill` 教它將已驗證且
有重用價值的流程儲存為筆記庫技能。流程規則全部在 `SKILL.md` 中，使用一般筆記
庫檔案工具。成功一次即可考慮儲存，無需逐份草稿再審批。
代理優先完善既有技能，避免近似重複，並就地替換被使用者更正的舊步驟。未經驗證
的嘗試留作帶日期的觀察，不冒充已跑通的流程。新增和修改的技能在下一使用者輪次
載入；儲存技能本身不會執行它。
詳見[記憶與過往對話](tools.zh-TW.md#記憶與過往對話)。

### 內建檔案與更新

Piem 從與目前外掛版本相符的 GitHub Release 下載內建 Markdown 資源，校驗外掛
中記錄的摘要後，在筆記庫中建立真實檔案。目錄在 Obsidian 裡可見，可以像其他
筆記一樣開啟、搜尋、同步。描述直接來自技能檔案，因此自帶的英文描述不會隨
介面語言切換。

**首次安裝需要連線到 GitHub。** 工作區就緒後開始準備，不會阻擋聊天。下載失敗
時，既有技能仍可離線使用。**設定 → Piem → 擴充能力 → 內建技能檔案** 顯示
結果，並提供 **重試準備**。背景不會迴圈重試，一般訊息也不會觸發下載。

更新只替換與安裝記錄仍一致的檔案。你改過的檔案和原先已有的檔案都會保留，
衝突列在設定中。刪除一個內建技能後，它會保持移除；**還原缺失檔案** 可以重新
建立缺失檔案，但不會覆蓋你的修改，也不會重新啟用已關閉的技能。目前版本不再
提供的檔案會留下供你查看。同步與更新不是跨裝置交易；所有權證據不一致時，
保留檔案而不覆蓋。

需要客製某個預設技能時，把它的資料夾複製到 `Piem/skills/`，保留相同技能名。
你的副本優先，官方版本仍可更新。內建資源只包含 Markdown，不安裝或執行指令
稿。下載涉及的資料說明見[安全與隱私](security.zh-TW.md)。

### 寫一個

一份 `SKILL.md` 需要兩個 frontmatter 欄位：

```markdown
---
name: weekly-review
description: 收集本週的日記筆記，據此起草一份週回顧。
---

讀最近七天的每篇日記筆記。把標了 #decision 或 #blocked 的內容挑出來。用
Templates/Weekly.md 的範本，在 Reviews/ 下起草一份回顧。
```

- `name` —— 只能是小寫字母、數字和連字號，並且必須與所在目錄同名。
- `description` —— 模型在判斷這個技能是否適用時讀的就是它。寫給模型看，不是
  寫給自己看。

Piem 使用 Pi 的技能載入器和提示詞格式化器，採用
[Agent Skills 格式](https://agentskills.io/specification)。模型先看到技能名稱、
描述和位置組成的目錄；需要某項技能時，呼叫 `read_skill` 取得正文，你輸入
`/名字` 也能直接提供正文。引用檔案再按需單獨讀取。這就是
**漸進式揭露**：程式把正文快取到記憶體，不代表把全部正文都放進模型上下文。

每個新的使用者輪次開始前會重新讀取技能：改一個、加一個，**下一則訊息**就生效，
不用重載外掛。已關閉的技能會被排除；`disable-model-invocation: true` 會把技能
從模型目錄中隱藏，但仍可顯式呼叫。

`read_skill` 每頁最多提供 50 KiB，並告訴模型如何續讀，不會切壞字元。
續讀攜帶內容指紋：檔案變了就從頭讀取，避免混用兩個版本。同一工具也能按技能
名和相對路徑讀取引用的 UTF-8 文字，包括桌面端的使用者層級技能。資源必須位於該
技能目錄內，不包含隱藏路徑段，單檔不超過 1 MiB；符號連結也不能越界。
筆記庫中的圖片仍可透過 `read` 讀取。Piem 不提供執行技能指令稿的 shell。

透過 `read_skill` 或 `/名字` 載入過的指令會在對話壓縮後保留原文，包括讀過的
引用頁。重複頁只保留一份，新載入的版本替換先前保留的舊版；子代理和重新開啟
的聊天也適用，介面不會重複顯示這些保留副本。未啟用的技能仍只提供目錄資訊。

在 **擴充能力** 中，徽章顯示 **內建**、**全域** 或 **筆記庫**。內建和筆記庫
檔案有 **開啟** 按鈕；匯入的筆記庫技能還保留來源 URL、更新和刪除操作。問題
列在對應來源旁。**重新載入** 只重讀本機檔案，不下載或還原檔案。資料夾搜尋
報告區分空目錄、缺失目錄和無法讀取的目錄。正在回答的對話會保留目前技能快照，
下一則訊息再使用更新後的內容。

### 從 GitHub 匯入

**設定 → Piem → Extensions** 支援直接從 GitHub URL 匯入技能：選一個儲存庫或子
目錄，先看計畫，然後 Piem 把那些 `SKILL.md` 寫進 `Piem/skills/`，同時留一份
來源記錄（provenance sidecar）。**Update** 按鈕日後能重新抓取，靠的就是那份
記錄。

資料夾 URL 會一起匯入 `SKILL.md` 和 Markdown 引用，指向單個技能或技能集合
都適用。單檔 URL 只匯入那一個檔案。指令稿等非 Markdown 檔案會在下載前跳過。
每次最多匯入 10 個技能、40 個 Markdown 檔案，單檔最多 256 KiB；超限會報錯，
不會悄悄丟掉 Markdown 資源。寫入失敗也會如實報告，不宣稱安裝成功。

舊版透過單個資料夾匯入、但缺少引用的技能，可以選擇 **Update** 補齊。即使遠端
目錄沒有變化，Piem 也會核對檔案集合，並保留原來的安裝目錄；本機修改仍會產生
衝突提示。

## 提示範本

提示範本放在筆記庫裡的 `Piem/prompts`，出現在同一套 `/` 自動完成裡，並標註來
源。

如果一個範本和一個技能同名，範本優先，技能仍可透過 `/skill:名字` 存取。在自
動完成裡選中它時，會自動插入那個消歧形式。

## MCP 伺服器

Piem 透過 Streamable HTTP 連線遠端 MCP（Model Context Protocol）伺服器，把它
們的工具併入代理自己的工具表。在 **設定 → Piem → Extensions** 裡設定：每個伺
服器是一個 http(s) URL、一個可選的 Bearer 權杖，和一個啟用開關。

- 工具對模型呈現為 `mcp_<伺服器>_<工具>`，任何一份對話記錄裡都能分清遠端工具
  和筆記庫工具。與既有工具重名時用數字後綴消歧。
- 伺服器名稱旁的徽章顯示 **已連線** 及工具數、**連線中**、**連線失敗**、
  **待連線** 或 **已停用**。開關決定是否啟用，徽章說明實際連線結果；錯誤原文
  保留在名稱下方。
- 儲存設定會連線已啟用的伺服器，尚未開啟聊天時也一樣。URL 和權杖都沒變的已
  連線伺服器保持不動；改過的或失敗過的會重新連線。待連線行旁有 **連線** 按鈕，
  失敗行旁有 **重試連線** 按鈕，可立即再試。傳送新訊息也會重新整理工具表；背景不
  會定時重試。
- 伺服器編輯器裡的 **測試** 按鈕探測草稿設定，不必先儲存。
- Bearer 權杖與服務商 API 金鑰走同一套落盤密封生命週期。見
  [安全與隱私](security.zh-TW.md#你的密鑰存在哪)。
- 逾時是有界的：連線並列出工具 15 秒，單次工具呼叫 120 秒，工具輸出按與其他
  工具相同的位元組預算截斷。

### 為什麼只支援遠端

不支援 stdio 傳輸。它要拉起子行程，而這在手機上是禁區——這個外掛在手機上是一
等公民，不是事後想起來的補丁。一個在手機上不可能存在的能力，寧可對所有人都
不做，也不做成桌面端的意外驚喜。

也沒有 OAuth 流程。一個靜態 Bearer 權杖足以涵蓋一個個人筆記庫現實中會對話的那
些伺服器，而它替掉的那套流程需要一次瀏覽器往返——Obsidian 並不適合承載它。

## 內建 Pi 擴充

Piem 內建了 Pi 官方原版的 **bookmark（書籤）** 擴充。開啟一段對話，然後使用
Obsidian 命令面板：

- **Piem: 為最近回覆加書籤**：輸入 1–160 個字元的標籤。
- **Piem: 移除最近書籤**：移除最後一條帶標籤記錄的書籤。
- **Piem: 檢視對話書籤**：搜尋標籤和回覆摘要，選擇一項閱讀。長回覆顯示前
  4000 個字元。

書籤直接儲存在既有對話檔案中，重載後仍在，也隨該檔案一起同步。分叉複製對話
時，保留複製範圍內回覆的標籤。即使儲存前切換了聊天，書籤仍屬於開啟彈窗時的
那段對話。寫入完成後才提示成功；失敗時保留輸入，可以重試。使用這些命令前，
請等待這段對話的回覆、重試或整理完成。

選擇規則沿用 Pi 原版：**整份對話日誌中最後追加的助手回覆**，包括回退後仍
保留的回覆。因此，它可能與介面目前顯示的最後一條不同。移除書籤也按記錄順序
倒著找，不按標籤的設定時間排序。同一標籤被兩端同時修改時，遵循既有工作階段合併
規則：以同步到來的檔案為準。同步不是跨裝置交易。

書籤可以離線使用。另外七項社群擴充也已內建，預設啟用。診斷分享可在
**擴充能力** 中關閉。

| 擴充 | 能做什麼 | 使用方法 |
| --- | --- | --- |
| `pi-assistant-provenance` | 告訴接手模型，前面的回覆由另一個模型寫成 | 自動生效，只加入請求上下文 |
| `pi-model-switch` | 查詢、搜尋和切換已設定模型 | 讓代理呼叫 `switch_model` |
| `pi-invisible-continue` | 接著目前任務做，不給模型額外塞入提示文字 | 輸入 `/continue`，或選擇 **Piem: 繼續目前任務** |
| `pi-web-search` | 用目前服務商搜尋網路，回傳來源連結 | 讓代理呼叫 `web_search` |
| `pi-clarify` | 把零散請求整理成可編輯的草稿 | `/clarify <想法>`，或 **Piem: 傳送前整理草稿** |
| `pi-context` | 儲存檢查點、查看時間線、從摘要分支繼續 | 讓代理呼叫 `context_checkpoint`、`context_timeline` 或 `context_compact` |
| [`b1tank/pi-otel`](https://github.com/b1tank/pi-otel) | 向 Piem 維護者分享錯誤報告與效能資料 | 預設開啟；在 **擴充能力** 中關閉 **分享錯誤報告與效能資料** 即可停止 |

切換只允許已有 API 金鑰、且服務商與模型編號組合唯一的模型。它會改變該對話的
下一次請求，並儲存預設選擇。新的服務商透過 Piem 原有網路通道收到對話內容；
上游顯示零價格代表費用未知，並非免費。儲存失敗會作為工具錯誤回報。其他聊天
已經開始的請求仍使用原來的模型。

`/continue` 會發出正常模型請求，攜帶既有對話及 Piem 原有的筆記上下文。正在
回答時，它在目前對話的佇列裡等待；停止會取消排隊。空標記隨聊天儲存，但不會
發給模型，重新開啟聊天後也一樣。`/continue status` 和 `/continue help` 顯示
上游診斷說明。若已有同名範本或技能，原命令保留短名；擴充使用
`/extension:continue`，也可在斜線選單中選擇。

`web_search` 重用目前模型的憑證。介面必須支援 OpenAI Responses 或 Anthropic
Messages 原生搜尋；一般 Chat Completions 介面能聊天，不代表能搜尋。搜尋可能
額外計費。查詢和指定網址發給該服務商，不額外攜帶整段聊天歷史。不支援時明確
報錯，不會換一家服務商。上游僅供 Gemini 使用的 `url_context` 不會出現在 Piem
目前支援的設定協定中；讀取已知網址仍可用 `web_fetch`。

`/clarify <想法>` 改寫命令後的文字；命令面板入口改寫輸入框裡既有的草稿。
請求中加上 `-clarify` 也會回傳草稿。你可以修改後再決定傳送。停止、關閉面板
或切換聊天後，遲到結果不會替換另一份草稿。等待時繼續輸入，新文字會保留，
未採用的改寫顯示在錯誤訊息裡。改寫只傳送草稿和上游改寫指引，不帶聊天歷史或
目前筆記。原版指引要求保留語言與原意，但偏重技術術語，一般筆記請求請看過再發。

預設使用目前對話模型。`/clarify model <服務商> <模型>` 可固定一個已設定憑證的
模型，`/clarify model reset` 恢復預設。選擇儲存到外掛設定，重載後仍在。固定
模型屬於另一服務商時，那家服務商會收到草稿。

`context_checkpoint` 儲存標籤後才回報成功。`context_compact` 儲存摘要分支、
選中它，再發起一輪模型請求繼續任務。舊分支保留在聊天檔案裡；筆記和外部操作
不會回滾。停止會取消待發的繼續任務。已經開始的 Vault 寫入可能完成，介面會
以最終儲存的歷史為準。`/context` 或 **Piem: 查看對話上下文用量** 開啟既有用量
面板，取代上游僅供終端使用的介面。

若技能或範本與擴充命令同名，原命令保留短名；用 `/extension:clarify` 或
`/extension:context` 明確選擇擴充。

`b1tank/pi-otel` 從固定 Git 提交安裝，與其他擴充一樣經過審核並由原版工廠載入。
Piem 沒有複製或移植它的原始碼；它也不是 npm 上的同名套件。它預設向固定位址
`https://otlppiem.shangxin.me` 傳送 OTLP/HTTP JSON，可在
[設定](settings.zh-TW.md#extensions) 中關閉分享，停止後續報告。
正文擷取關閉，但模型錯誤文字可能含筆記內容，詳見
[安全與隱私](security.zh-TW.md#opentelemetry-發送)。其事件涵蓋主對話，不含
所有子代理內部模型呼叫。

這些擴充隨 `main.js` 分發，只透過正常外掛發布更新。Piem 不會從筆記庫或 URL
下載、執行 JS/TS 擴充。上游的 `aliases.json`、來源標註 `config.json` 等設定檔
沒有掛載，擴充使用預設行為。

開發者可查看[相容橋指南](pi-extension-bridge.md)，了解支援範圍、原始碼審核
和驗證方法。橋重用 Pi 原版工廠載入器、執行器、事件匯流排及工具包裝器。書籤和
社群擴充都使用同一個宿主實作；既有 Pi 代理及工作階段儲存仍是唯一資料來源。
歸屬與授權見[第三方聲明](../THIRD_PARTY_NOTICES.md)。

## 開發內建技能

儲存庫中的 `skills/<名字>/SKILL.md` 是內容的唯一來源。新增帶 `name` 和
`description` 檔頭的合法目錄，建置就會自動發現，無需往 TypeScript 登記。
Markdown 引用和範本會保留相對路徑，隨技能一起分發。建置會拒絕缺失中繼資料、
不安全路徑、指令稿、符號連結和不存在的連結資源。

`npm run build` 產生 `dist/builtin-skills.json`，並把摘要寫入 `main.js`；
`npm run check:skills` 檢查兩者與原始檔案是否一致。發布流程將資源與三個標準
外掛檔案一起上傳，並產生來源證明。

`npm run dev` 會監視新增、修改和刪除，並在 `main.js` 旁產生相同 JSON。
把這兩個檔案複製到開發用外掛目錄後重載 Piem；開發建置讀取本機 JSON，不需要
先發布 Release。正式建置始終下載與已安裝版本相符的資源。
