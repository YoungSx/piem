# セキュリティとプライバシー

[← README に戻る](../README.ja.md) · [English](security.md) · [简体中文](security.zh-CN.md) · [繁體中文](security.zh-TW.md)

Piem はあなたのノートをモデルプロバイダーに渡し、エージェントにそれを編集さ
せます。この 2 つはどちらも本質であり、設定タブの中で自分で見つけさせるので
はなく、はっきりと述べておくに値します。

## 何がボールトを出ていくか

設定したモデルプロバイダーへ送られるもの：

- あなたのプロンプトと会話履歴；
- **あなたが開いているノート**——パスと全文——毎ターン送られます。あなたの質
  問がそれに関するものかどうかは関係ありません；
- ツールが返したボールトの内容——ノート本文、検索結果、ファイル一覧、
  frontmatter；
- エージェントが思い出したときの、保存済みメモリと過去の会話の抜粋；
- ツールの結果。`web_fetch` が持ち帰ったものを含みます；
- あなたがステージングした画像添付。

MCP サーバーへは、加えて次のものが送られます：そのサーバーが公開するツールの
呼び出し引数。各 MCP ツールの説明はそのことを自らのテキストで述べているので、
モデルもそれを知っています。

組み込みスキルの準備では、インストール済みのプラグインバージョンに対応する
リソースを取得するために GitHub へ GET リクエストを送ります。GitHub とその
ダウンロードホストは、リソース URL（そのバージョンを含む）、デバイスの IP
アドレス、通常のリクエストメタデータを受け取ります。このダウンロードにボー
ルトのノート、会話内容、プロバイダーの鍵は同行しません。リソースはチェック
サム検証済みの Markdown で、`Piem/builtin-skills/` の下に書き込まれます。スク
リプトは実行されず、プラグインとは独立して新しいリリースを追うこともありませ
ん。

組み込みの `switch_model` は、あなたが API 鍵を設定した別のモデルに現在の会話
を移し、その選択を保存できます。そのプロバイダーは次のリクエストで会話と通常
のノートコンテキストを受け取ります。`/continue` は通常の課金対象となるモデル
リクエストを開始します。来歴の注記はリクエストコンテキスト内で以前のモデル名
を挙げるだけで、別のサービスへ何かを送ることはありません。これらの拡張はプラ
グインに同梱されたコードだけを実行し、ローカルやリモートのスクリプトを読み込
むことはできません。

`web_search` はそのクエリと与えられた URL を現在のモデルプロバイダーのネイ
ティブ検索エンドポイントへ送り、会話全体をその検索リクエストに加えることはあ
りません。検索とソースの取得はプロバイダーが担い、そのプロバイダー独自の規約
と検索料金が適用されます。Piem が黙って別のプロバイダーを選ぶことはありませ
ん。`/clarify` は与えられた下書きと書き換え指示だけを、現在の、あるいは明示
的にピン留めしたモデルへ送ります。アクティブなノートや会話は加えません。結果
はあなたが送信するまで編集可能な下書きのままです。`context_compact` は古い履
歴を保持して要約ブランチをローカルに保存し、続けるために通常のモデルリクエス
トを送ります。

停止は保留中の拡張アクションを取り消し、遅れて届いた結果を無視します。
Obsidian の `requestUrl` は既に発行済みのネイティブネットワークリクエストを止
められないので、そのリクエストは完了する、あるいは課金対象のまま残ることがあ
ります。保留中の転送作業は決着するまで勘定に入れられ続けますが、遅れて下書き
を書いたり、別のチャットを切り替えたり、停止したタスクを再開したりはできませ
ん。

エラー報告とパフォーマンスデータは既定で Piem のメンテナーへ送られます。以下
で述べるとおり、**設定 → Piem → 拡張機能** で共有をオフにできます。

実践的な帰結：**Piem を向けるのは、あなたのモデルプロバイダーへ送っても構わ
ないボールトにすること。** あるファイルに触れる検索はそのファイルを一覧に挙
げ、モデルはその一覧を見ます。

## OpenTelemetry の送信

同梱された原版の `b1tank/pi-otel` 拡張は、トレース、メトリクス、ライフサイク
ルログを Piem のメンテナーの `https://otlppiem.shangxin.me` へ送ります。
**設定 → Piem → 拡張機能 → エラー報告とパフォーマンスデータを共有** は既定で
オンです。オフにすると新しい報告を即座に止め、未送信データを破棄します。既に
送られたリクエストは呼び戻せません。オンに戻すには共有を再開するために Piem
の再読み込みが必要です。送信先は送出されるデータに加えて、デバイスの IP と通
常の HTTP メタデータを受け取ります。これらの報告は匿名ではありません。

送信内容にはセッション ID、モデルとツールの名前、タイミング、トークン使用量、
報告されたコスト、成功か失敗かの状態が含まれます。プロンプト、応答、システム
指示、ツールの引数と結果、セッションパス、プロバイダーのペイロード／ヘッダー
の取得はオフのままです。**モデルのエラーメッセージは依然としてスパンのステー
タスと例外イベントに入る**ので、ノートのテキストを含むエラーは、内容取得がオ
フでもそのテキストを送ってしまうことがあります。Collector は機微な診断情報の
送信先だと考えてください。

Piem はホストが管理するバックグラウンドの `requestUrl` 転送を通じて、固定アド
レスに `/v1/traces`、`/v1/metrics`、`/v1/logs` を付けた OTLP/HTTP JSON を送り
ます。送信先は設定で編集できず、以前のカスタムアドレスは使われません。認証は
ゲートウェイ側で処理され、Collector の資格情報はプラグインに含まれません。プ
ロバイダーの鍵とコンピューターの環境変数は拡張に渡されません。あなたの共有設
定はプラグインデータに保存され、ボールト同期で運ばれることがあります。

メトリクスは 60 秒ごとに、トレースとログはそれぞれ独自のバッチで送られます。
会話を閉じたり Piem をアンロードしたりすると、所有するタイマーが止まり、有界
の最終フラッシュが許されます。Collector が利用できない、あるいは遅いと、その
最終バッチが失われることがあります。停止は現在の回答を終えますが、その会話の
テレメトリはアクティブなままにします。既に送られたネイティブリクエストは、ホ
ストが待つのをやめた後に完了することがあります。この統合はすべての内部サブエ
ージェント呼び出しをトレースするわけではありません。

## 確認ステップは存在しない

エージェントは `write`、`edit`、`move_note`、`trash_note` を即座に行えます。ダ
イアログも、承認すべき diff も、「本当によろしいですか」もありません。

一つだけ例外があり、それはダイアログとして描かれるのではなくコードで強制され
ます：設定ディレクトリ（`.obsidian/`）は読み取り専用です。エージェントはあな
たの設定とインストール済みプラグインのデータを読めますが——
[エージェントのツール](tools.md#the-agents-tools)を参照——そこへの書き込みの
試みはすべて明示的な拒否として返ってきます。

これは意図的なプロダクトの決定であって、欠けている機能ではありません。それに
どう対処するか：

- 変更されても構わないボールトで Piem を使う。
- 各ターンの後に会話記録を読む——どの変更もツール呼び出しから来ており、どの
  ツール呼び出しもそこにあります。
- ボールトをバージョン管理下に置くか、Obsidian のファイル復元に頼る。
  `trash_note` は Obsidian のゴミ箱を通るので、削除は通常のやり方で復元できま
  す。

## あなたの鍵はどこにあるか

メモリのノートは普通の Markdown で、ボールトとともに保存・同期されます。
`vault-memory` スキルはエージェントに鍵とパスワードを避けるよう指示しますが、
それは秘密の検出器ではありません。復元はあなたのボールトのファイル復元または
バージョン管理に依存します。現在の事実を消しても、その日付ログ、元となった
チャット、それら復元システム内のコピーは削除されません。
[メモリと過去の会話](tools.md#memory-and-past-conversations)を参照。

API 鍵と MCP のベアラートークンは Obsidian のプラグインデータとともに保存され
ます。

- **デスクトップ：** `data.json` に書き込む前に Electron の `safeStorage` で封
  印されます——Windows では DPAPI、macOS では Keychain、Linux では libsecret。
- **モバイル、およびキーリングのないデスクトップ：** `data.json` の中に平文で
  入ります。封印に使えるものがなく、あるふりをするのは正直に言うより悪いこと
  です。

封印された鍵は、それを封印したデバイスの上でしか復号できません。したがって
ボールト同期は使える鍵をデバイス間で運び**ません**：鍵はデバイスごとに一度ず
つ入力してください。これは制限というより機能ですが、「なぜ携帯電話では鍵が空
なのか」の答えがここにあることも意味します。

制限付き、あるいは低い上限の鍵を使うのが望ましいです。プラグインはそれをあな
たに代わって強制できません。

## Obsidian のレビューが指摘する能力

Piem はエージェントプラグインなので、その仕事をこなすには Obsidian のコミュニ
ティプラグインレビューが明示的に報告する能力が必要になります。ここではそのレ
ビューと同じ語彙でそれらを挙げます。どれも欠陥でも回避策でもありません——それ
ぞれがある機能を支えており、どれも上で述べた以外のどこへも何かを送ることはあ
りません。

**直接のファイルシステムアクセス。** デスクトップでは、プラグインは Electron
の `require` を通じて Node の `fs` に手を伸ばし、ユーザーレベルのスキルフォル
ダー（`~/.pi/agent/skills`、`~/.agents/skills`、およびあなたが設定する追加の
ディレクトリ）を読みます。ボールト API はこれらのファイルを見られません。
`read_skill` は選択されたスキルの UTF-8 テキストリソースを必要に応じて読めま
す：各ファイルは 1 MiB を上限とし、正規パスの検査でそのスキルのディレクトリ
内に留めます。絶対パス、隠しパス、親への遡り、外へ逃げるシンボリックリンクは
拒否されます。読み込まれたテキストは他のツール結果と同様にアクティブなモデル
へ送られ、既に読み込まれたリソースは圧縮を越えて保持されます。これは読み取り
専用のアクセスであり、シェルの実行は提供しません。普通のボールトツールはボー
ルトに限定されたままです。モバイルではホストが `require` を公開しないので、
ユーザーレベルのスキルはプラグインを失敗させるのではなく利用不可として現れま
す。

**ボールトの列挙。** 検索とタスクのツールは `vault.getFiles` /
`vault.getMarkdownFiles` を呼び、ボールト内のすべてのファイルをその完全なパス
とともに列挙します。検索やタスクのクエリがそれらに触れるたびに、モデルはその
一覧を見ます。それは「私のボールトを検索する」ということに内在するものです。

**クリップボードアクセス。** 出ていくだけ：メッセージの返信、ログ行、設定内の
シークレットのコピー機能が `navigator.clipboard.writeText` を呼びます。Piem は
クリップボードを決して読みません。貼り付けられた画像はクリップボードの読み取
りではなく、エディター自身の paste イベントを通じて届きます。

**実行時の base64 エンコード。** 画像添付はモデルのコンテンツとして送られる前
に `btoa` でエンコードされます。それが用途のすべてです——コードのどこにも、難
読化されたペイロードをデコードする箇所はありません。

**ネットワークリクエスト。** およそ 20 か所の呼び出し地点、そのすべてが一つの
転送層を通ります：モデルプロバイダーのストリーム、接続テスト、models.dev のカ
タログ提案、リモートの MCP サーバー、スキルのインポート、組み込みスキルの準
備、`web_fetch` ツール、そして診断共有がオンの間の Piem の OpenTelemetry
Collector。`requestUrl` と `fetch` のあなたの選択は、ストリーミングが重要な
リクエスト——モデルストリームと接続テスト——を舵取りします。カタログ、スキルの
インポート、組み込みスキルの準備、`web_fetch`、テレメトリは常に `requestUrl`
に乗ります。なぜなら応答全体を取得し、CORS ヘッダーを送らないホストに届かなけ
ればならないからです。送出は、コードベース各所に散らばるのではなく、一か所で
点検可能なままです。

組み込みの準備は 15 秒後に待つのをやめ、失敗しても繰り返しません。アンロード
は準備を取り消し、遅れて届いた応答がファイル書き込みを始めないようにします。
Obsidian の `requestUrl` は既に発行済みのリクエストを物理的に取り消せないので、
基底のリクエストはプラグインが待つのをやめた後に完了することがあります。既存
のファイルはオフラインで使えます。拡張機能内の **準備を再試行** と
**欠けているファイルを復元** のアクションは明示的な復旧経路です。

## 何かを報告する

Piem に上記で説明していないことをさせる方法を見つけましたか？
[`YoungSx/piem`](https://github.com/YoungSx/piem/issues) で issue を開いてくだ
さい。もしそれが機微なものなら、最初の行でそう述べ、誰かが返信するまで詳細は
伏せておいてください。
